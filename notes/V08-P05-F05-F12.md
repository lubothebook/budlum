## F05: CONFIRMED, Medium

- cross_domain/relayer.rs:332-337 records the ledger entry (`self.ledger.record`) before relayer.rs:340-349, which check that the event carries a message and that `verify_id` holds. On either error the ledger record stays and `pending` is not removed (removal is at :352). Any retry hits relayer.rs:280-282 and gets AlreadyRelayed.
- Production trigger for that half: none found. The only production enqueue is chain/blockchain.rs:2897 (enqueue_bridge_relay), which is called from lock and burn at blockchain.rs:2265-2266 and 2344-2346, right after `submit_cross_domain_message` passed `verify_id` (blockchain.rs:2279). The message is cloned from the event itself, so `message: None` and a bad id cannot reach it. Treat it as a latent ordering defect.
- The blockchain half is reachable. chain/blockchain.rs:3268-3282: `process_relay` mutates the relayer (ledger record plus pending removal) and the relayer state is persisted at 3278-3282. After that, the following steps can fail and return Err with no rollback of the relayer: `get_transfer` at 3291-3296, `split_bridge_fee` at 3299-3304, `ensure_mint_headroom` at 3308-3313, `bridge_state.mint` at 3314-3317 (for example, status not Locked or nonce already processed), and the burn arm's correlation, domain and unlock checks at 3340-3365. Once that happens the relay is consumed for good and nothing is minted or unlocked.
- Impact. Mint side: the transfer stays Locked, and the sweep refunds the owner at expiry (bridge.rs:727-740). The recipient gets nothing and no funds are created. Burn side: the transfer stays Burned and has no exit (the F02 class).
- Note: `sweep_retired` (relayer.rs:403-411) drops ledger records after RELAY_RETENTION_BLOCKS = 10,000 (relayer.rs:173, nonce.rs:10), so "every retry, for ever" is really "until retention passes". By then the pending entry is normally expired as well.
- Entry point: rpc/server.rs:2843-2866, gated by `require_operator` at :2858. chain_actor.rs:3855.

## F06: CONFIRMED, Medium (with a possible High sub-finding)

- cross_domain/message_registry.rs:20-32: `insert` checks only `verify_id` and duplicates. cross_domain/message.rs:88-109: the id is a hash of fields the caller supplies, so a caller can always produce a consistent id.
- chain/blockchain.rs:2875-2883: `submit_relayed_cross_domain_message` gates on `ensure_active_relayer(&message.sender)`. The sender is a self-declared field and no signature is checked.
- Entry points with no operator gate:
  - rpc/server.rs:2661-2681 (`bud_submitCrossDomainMessage`, api.rs:290). This handler never calls `require_operator`, so it is live on the public listener.
  - network/node.rs:2859-2880: a gossiped CrossDomainMessage from any peer goes to the same function and is then re-broadcast.
- Consequences. Anyone can name an active relayer as sender and register arbitrary messages, including Custom kinds and unbounded payloads (see F07). They can also pre-register a message id to make a later lock or burn fail at blockchain.rs:2304 (see F11). The lock id depends on a predictable bridge nonce plus the operator's inputs (message.rs:88-105), so pre-registering it needs those inputs guessed or observed. That step is Likely, not Certain.
- Production path: yes.

## F07: CONFIRMED, Medium

- message_registry.rs:8-67 has no remove, prune or retention method. A repo-wide search for `message_registry` (chain/blockchain.rs, core/account.rs) finds only insert, root and wholesale replace (blockchain.rs:837, 5328).
- `root()` (message_registry.rs:50-67) hashes every message. It is called at blockchain.rs:867 (load), 1916 (`apply_block_end_roots`, every block) and 1950 (`build_global_header`). The result goes into the state root at core/account.rs:2450.
- message.rs:14: `Custom(Vec<u8>)` has no length bound. The only limit is the RPC or gossip frame size.
- Production path: yes. Through F06 any peer can grow the registry. Cost per block and state size grow without limit.

## F08: CONFIRMED, Low to Medium (integration)

- relayer.rs:11-14 promises slashing for invalid proofs and for missed deadlines. relayer.rs:176-197 defines `relay_window_blocks`, `min_relayer_stake`, `slash_ratio_invalid` and `slash_ratio_expired`. A search over src/, budzero/ and crates/ finds no use outside relayer.rs (including its tests at :616).
- `Blockchain::expired_relays` (blockchain.rs:3425-3432) has no caller. `UniversalRelayer::expired_relays` (relayer.rs:373) is called only from it and from tests (relayer.rs:589, 592, 662).
- Both functions are in the baseline: .github/idle-code-baseline.txt:1183 (blockchain) and :1424 (relayer). The four config fields are not listed in it.
- Invalid-proof slashing does exist through evidence.rs:305 and 688-722, with its own 100% ratio, so `slash_ratio_invalid` contradicts it and is dead. There is no slashing kind for a missed relay.
- Production path: none; it is idle code. The real risk is a wrong security claim in the docs.

## F09: CONFIRMED, Low today

- cross_domain/evm/bud_to_eth.rs:90-137: `build_bud_to_eth_claim` takes `recipient_eth: [u8; 20]` as a free argument and copies it into the claim (:132). Nothing ties it to the burn transfer or the burn message, and those carry only a 32-byte Budlum `recipient`.
- The same transfer only has to be Burned (:107). The source-side unlock also consumes Burned transfers (blockchain.rs:3347-3365), so the two exits are not exclusive. This is the F01 class.
- `BudToEthError::InvalidRecipient` is never built (see F20).
- Callers: none outside the file. The only mention is evm/mod.rs:24 (`pub mod`). bin/budlum-relayer.rs:685-747 only scans for burns and states that Ethereum submission is not available (:700).
- No Solidity bridge contract is in the repo (contracts/ holds only the verifier, per AGENT_MAP).

## F10: CONFIRMED, Low

- cross_domain/bridge_relayer.rs:11 says "WIRING: unwired". The pipeline struct is at :81. Its only reference outside the file is the re-export at cross_domain/mod.rs:13.
- Baseline: idle-code-baseline.txt:1395-1397.
- It clones the whole BridgeState on every call: `let before = self.bridge.clone()` at :144 (lock) and :250 (burn).

## F11: CONFIRMED (order); PARTLY (reachability)

- Lock: chain/blockchain.rs:2243-2258 calls `bridge_state.lock` (row, nonce, expiry entry). It debits the owner at :2259-2260 and saves bridge state to disk at :2262-2264. Only then is `submit_cross_domain_message` called (:2266). If that returns Err, nothing is undone and no relay is queued.
  - Impact is temporary: the row is Locked, so the sweep refunds the owner at expiry.
  - Production caller: none found. `Blockchain::lock_bridge_transfer` is reached only through chain_actor.rs:2417 and 4072, and nothing outside tests calls `ChainHandle::lock_bridge_transfer`. rpc/api.rs:307-312 describes the lock RPC as removed.
- Burn: blockchain.rs:2330-2346 calls `burn_with_event` (sets Burned) and saves to disk before `submit_cross_domain_message` (:2344). A refusal leaves a Burned row with no burn message and no pending relay, which is permanent (the F02 class).
  - Reachable through the operator RPC (rpc/server.rs:2760-2769, gated at :2769).
  - Combined with F06, a public caller can force the refusal by pre-registering the burn message id. The correlated burn id depends on the operator's arguments (domain_height, event_index, expiry), so this is Likely, not Certain.
  - For the burn half, severity rises from Low to Medium.

## F12: CONFIRMED, Low

- relayer.rs:296: a relay is expired only when `current_height > expiry`, so it is still valid at height == expiry. bridge.rs:727-733: the sweep takes `expiry_queue.range(..=current_height)`, so a refund is also allowed at height == expiry.
- bridge.rs:432-502: `mint` never reads `message.expiry_height`. The executor mint path (executor.rs:1174-1180) does not read it either.
- In-block, the sweep runs after transaction execution (blockchain.rs:4571 calls `apply_bridge_sweep_to_state`), so ordering inside a block is deterministic: the mint wins.
- The divergence claim holds only for `Blockchain::submit_relay_proof` (the operator RPC), which mutates state outside blocks using `chain.len()` as height (blockchain.rs:3241).
- There is no double credit, because both exits are status-gated.

## New sub-findings

- F06-a (High, Likely; needs a check of block-validation root comparison). `message_root` is part of the state root (core/account.rs:2450, blockchain.rs:1916). Messages enter `state.message_registry` outside block execution, through the public RPC (server.rs:2661) and gossip (node.rs:2866), at times that differ from node to node. Nodes can therefore compute different state roots for the same block, and any peer can trigger this because the sender is unauthenticated. This is a consensus-split or liveness vector.
- F05-a (Medium, Certain). `submit_relay_proof` (blockchain.rs:3229-3389) applies the mint or unlock credits outside block execution on a single node; the server.rs:2850-2857 comment admits it. The relay ledger and bridge roots therefore diverge from peers, and so does the state root through `bridge_root`. Already logged as an open design item (E-7), but it is not listed in FINDINGS.
- F11-a (Low, Certain). Both lock and burn persist bridge state to disk (blockchain.rs:2262, 2339) before the message registry accepts the message. A refusal leaves disk and memory agreeing on a half-done transition, so a restart does not heal it.
- F08-a (Info). The `slash_ratio_invalid` default of 50 (relayer.rs:193) contradicts the evidence path's 100% relayer slash (evidence.rs:305, 708). Two sources of truth, one of them dead.
- F09-a (Info). bud_to_eth.rs:118-122 truncates or zero-pads `asset_id` to 32 bytes with no length check. AssetId width is not verified here; this is harmless while the module is unwired.
